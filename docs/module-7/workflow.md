# Workflow

## Базовый цикл изменений

1. Заберите актуальную ветку и обновите зависимости при необходимости.
2. Внесите изменения небольшими логическими порциями.
3. Проверьте локально:
   - `npm run lint`
   - `npm run build`
4. Пройдитесь по критическим user-flow (главная, логин, оффер, избранное).
5. Подготовьте коммит с понятным сообщением, ориентированным на "почему".

## Практика для этого проекта

- Данные офферов и комментариев берём из API, не из моков.
- Для асинхронных сценариев обязательно выставлять loading/error флаги в store.
- Для offer-id использовать `string` (UUID), не `number`.
- Логику авторизации держать централизованно в thunk + token service.
- Не смешивать UI-данные и API-модели без явного преобразования (пример: `Comment -> Review`).

## Минимальный чек-лист перед PR

- `npm run lint` без новых ошибок.
- `npm run build` проходит успешно.
- Все новые роуты и редиректы проверены вручную.
- Нет оставшихся debug/instrumentation логов.
- Нет мертвых моков и неиспользуемых экспортов.
- Документация в `docs/module-7/` обновлена при изменении поведения.

## Стиль коммитов

- Один коммит = одна логическая задача (без смешивания unrelated правок).
- Сообщение коммита в повелительном стиле, коротко и по причине изменения.
- Рекомендуемый шаблон:
  - `feat: add offer comments loading flow`
  - `fix: handle 404 on offer page by id`
  - `docs: update module-7 architecture notes`
- Если изменение затрагивает API/state/UI, отражайте это в тексте коммита явно.

## Рекомендации по архитектуре изменений

- Новые API-сценарии оформлять в `src/store/api-actions.ts`.
- Изменения структуры данных синхронно отражать:
  - в `src/types/types.ts`,
  - в `src/store/reducer.ts`,
  - в соответствующих страницах/компонентах.
- В UI-компонентах избегать бизнес-логики; держать её в selector/thunk/reducer слое.

## Когда дорабатывать документацию

Обновляйте документы из `docs/module-7/`, если меняется хотя бы один из пунктов:
- состав state или набор thunk-ов;
- API endpoint или auth-поведение;
- роутинг приложения;
- правила валидации форм;
- workflow команды перед PR.
